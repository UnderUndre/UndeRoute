## Summary

Спецификация и архитектурный замысел `004-safe-harness-valves` (клапаны G1–G8) — мощная и глубоко обоснованная инженерная работа, опирающаяся на реальный эмпирический ресерч 13 failure modes вайбкодинга и прецедент Matter of Dhanasar (EB-2 NIW). Документация образцово структурирована, QA-контур (ISO 29119/29148) и RTM проработаны досконально, а бизнес-план v3.1 синхронизирован. Однако в сантехническом слое реализации обнаружены 4 критических «засора» (HIGH): подмена bind-mount каталога `/workspace` на RAM-диск `tmpfs` (что физически стирает результаты работы агента), калечный `seccomp.json` без `execve`/`clone`/`futex` (блокирующий запуск любых процессов в контейнере), запуск голого BusyBox `alpine:3.19` мимо `sandbox/Dockerfile`, и конкатенация строк в `dockerCmd` с дырой под host command injection.

| F1  | HIGH     | Architecture / Sandbox     | **`--tmpfs /workspace:rw` уничтожает персистентность репозитория и изолирует агента от кода** (`spec.md:50,161`, `plan.md:34` ADR-011, `tasks.md:14` T004). Монтировать workspace как bind-mount (`--volume "${config.workspacePath}:/workspace:rw"`), корень контейнера делать `--read-only`, а `tmpfs` выделять только под временные каталоги (`--tmpfs /tmp:rw,noexec,nosuid`, `--tmpfs /run:rw,noexec,nosuid`). Удалить упоминания `--tmpfs /workspace:rw` из spec/plan/tasks.                      |
| F2  | HIGH     | Security / Seccomp         | **`sandbox/seccomp.json` блокирует запуск любых бинарников и потоков** (`sandbox/seccomp.json:4-61`, `spec.md:50`, `tasks.md:14` T004). Любая попытка `/bin/sh` запустить дочерний процесс или попытка Node/Python поднять тред упадет с `EPERM`.  | Дополнить `sandbox/seccomp.json` минимальным набором системных вызовов POSIX-тулчейнов (`execve`, `clone3`, `futex`, `pipe2` и т.д.) либо взять за основу стандартный профиль Docker seccomp с точечной блокировкой опасных syscalls (`ptrace`, `bpf`, `mount`, `reboot`, `sys_*`). ## Alternative approaches considered

1. **Долговременный контейнер сессии (`docker exec`) против одноразовых (`docker run --rm`)**:  
   Текущая архитектура запускает новый контейнер `docker run --rm` на каждую команду. Это дает идеальную изоляцию, но полностью стирает контекст окружения между вызовами (например `cd subfolder` или `export FOO=bar` сбрасываются). Необходимо в системном промпте агента явно отразить, что вызовы bash являются stateless, требуя составных команд (`cd ... && npm test`).
2. **Использование стандартного Docker Seccomp Profile вместо рукописного allowlist**:  
   Построение default-deny allowlist с нуля на практике невероятно трудоемко из-за сотен скрытых вызовов musl/glibc и runtime тредов. Альтернативный и значительно более надежный путь — взять проверенный производственный профиль Docker Default Seccomp Profile и перевести в deny-лист специфические опасные системные вызовы (`ptrace`, `bpf`, `mount`, `reboot`, `sys_*`).
